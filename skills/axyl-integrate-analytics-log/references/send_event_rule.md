# SDK Log Send Rules

This document defines **what payload to send a selected event in**. Which events to select follows the
event design and code generation rules.

The supported scope is client SDK sending for Hive SDK v4 and Hive Axyl. It does not generate direct
server-send HTTP/Fluentd code.

## 1. Send Structure

The payload is flat JSON with the required properties and the event properties at the same level.

v4:

    {
      "eventName": "asset_get",
      "assetName": "dia",
      "amountPrev": 100,
      "amountCurr": 120,
      "guid": uuid()
    }

Axyl:

    {
      "deviceId": "3f9c2a7e1b4d4e8f9a6c5b2d1e0f7a8c",
      "eventTime": "2026-09-01T14:03:21+09:00",
      "eventName": "asset_get",
      "assetName": "dia",
      "amountPrev": 100,
      "amountCurr": 120,
      "guid": uuid()
    }

For Axyl, the game does not build the JSON above itself. Fill the `EventTime`, `EventName`, and `DeviceId` fields of
`ClientLogEvent` and its `AdditionalProperties` (event properties and guid), and the SDK serializes them into this structure.
`AdditionalProperties` values are strings holding JSON values (number `"100"`, string `"\"dia\""`). The server fills
identifierProvider with `hive`. Follow section 6 of the Hive Axyl SDK flow for the detailed rules.

Do not create the following in the game payload.

- attributes
- eventAttributes
- hiveAttributes
- category
- dataSource
- every property name starting with `_`

These are storage or pipeline metadata.
The Analytics system reassembles them into columns, attributes.hiveAttributes, and attributes.eventAttributes during data processing.
The `_` prefix is reserved for properties the analytics pipeline processes (`_dataSource`, `_geoIpCountry`, `_clientIp`, and so on).
Auto-collected SDK and header values carry no prefix.

`guid` is the diagnostic property that links the runtime send to the actual ingestion. For both SDKs, the game generates a UUID
string itself per event, puts it in the payload, and records the same value in the central send log. Even when the v4 SDK provides
its own `guid`, overwriting it with the value the game passed is allowed. `guid` is a common diagnostic property this skill
explicitly permits, and it can be sent even when it is absent from an event template's `get_event_spec` result.

## 2. Required Properties

| Property | Rule | Example |
|------|------|------|
| userId | Send the account-level user identifier as a string | `"100001"` |
| deviceId | Send the device-level user identifier as a string. For Axyl it is the DeviceKey (22–64 characters) | `"3f9c2a7e1b4d4e8f9a6c5b2d1e0f7a8c"` |
| identifierProvider | Fixed to `hive` for a Hive SDK integration | `"hive"` |
| appId | The app identifier registered in App Center and confirmed in the repository | `"com.example.game.android.google"` |
| appIdGroup | Sent instead of appId only in a separate design where appId is unavailable | `"com.example.game"` |
| eventTime | The event's occurrence time in RFC 3339 format, including the time zone | `"2026-09-01T14:03:21+09:00"` |
| eventName | Send exactly the name confirmed in the event definition | `"asset_get"` |

The table above is the final ingestion contract. Each SDK's automatic collection scope differs from the scope of required
properties it sends, so keep them distinct.

What the game passes, per SDK:

| SDK | Required properties the game puts in itself | Minimal example |
|-----|-----------------------------|-----------|
| Hive SDK v4 | eventName | `{"eventName":"asset_get"}` |
| Hive Axyl | deviceId, eventTime, eventName | `{"deviceId":"<DeviceKey>","eventTime":"2026-09-01T14:03:21+09:00","eventName":"asset_get"}` |

Axyl fills three of the required properties on the game's behalf: appId, userId, and identifierProvider. appId comes from the
X-App-Id the SDK sends, userId from the X-Hive-Player-Id the gateway fills, and the server always overwrites identifierProvider with `hive`. The game passes the remaining required properties and the GAME custom properties
directly, all at the same level.

Every other header is ingested into hiveAttributes without a prefix — `os`, `sdkVer`, `deviceId` — and does not fill a
required property. The full mapping follows section 2 of the Hive Axyl SDK flow.

Use the camelCase names in the table above exactly for the required property names. Changing them to snake_case, such as user_id or
event_name, prevents correct processing.

### appId / appIdGroup

- Axyl sends CoreConfig.CreateBuilder's appId as the X-App-Id header, and it is collected at the receiving stage as the required
  appId property. Do not put appId or appIdGroup in logBody.
- appIdGroup is generated by the pipeline from appId. If both values are put in, appIdGroup is regenerated from appId.
- Do not work around an AppID gate failure with an unknown value. If the gate does not pass, do not generate code.

### Handling a missing required value

If any required property is absent or empty, the entire log is quarantined into the rescue table. Even when a value cannot be
obtained, do not omit the property — fill it with `"0"` or `"unknown"` and send it.

- Settle eventName from the definition and design. If the event name is unknown, do not insert a fallback — do not create the send point.
- For eventTime, put in the actual event occurrence time directly. It is always obtainable, so do not use a fallback. For Axyl,
  put a `DateTimeOffset` in `ClientLogEvent.EventTime` and the SDK converts it to RFC 3339 including the UTC offset. If it is not
  set, `0001-01-01T00:00:00.0000000+00:00` is sent, so always set it.
- For Axyl, the server always overwrites identifierProvider with `hive`, so the game does not set it.
- For deviceId, confirm the Axyl DeviceKey the app creates, stores, and passes in the repository, and reuse the same value. Always
  send it, regardless of auth state. If a custom auth implementation owns DeviceKey creation and there is no existing value,
  generate a UUID-based value once and store it. If a Recipe or the auth module manages it internally and the exposure point
  cannot be confirmed, send `"0"` or `"unknown"` and report it as `needs further review: confirm the DeviceKey exposure point`.
- Do not put userId in the game payload. The gateway collects it from X-Hive-Player-Id, and a window with no header — such as
  before login — is filled with `"0"` at the receiving stage. Do not classify pre-login events as `not currently implementable`.
- For appId, confirm the CoreConfig initialization value at the integration gate. Do not put it in the game payload, but verify
  that it is sent correctly as X-App-Id.
- This rule applies to required properties only. For an event property whose value you do not know, do not insert an arbitrary
  fallback — leave it as an unconnected value source. An empty event property is not a quarantine reason.

## 3. eventTime

Any path that builds eventTime itself includes RFC 3339 format and the time zone. For Axyl SDK sending, the game does not
build the string — it puts a `DateTimeOffset` in `ClientLogEvent.EventTime`, and the SDK converts it to this format.

Allowed:

    2026-09-01T14:03:21+09:00
    2026-09-01T05:03:21Z
    2026-09-01T14:03:21.123+09:00

Quarantined:

    2026-09-01 14:03:21
    2026-09-01
    1788239001

A value older than 31 days in the past or more than 31 days in the future relative to the current time is quarantined. The pipeline
converts eventTime to UTC and stores it in the dateTime column, preserving the original in eventAttributes.

The field name to send is eventTime. Do not send it as dateTime or build eventAttributes yourself.

## 4. Event Properties

### Names

| Rule | Correct example | Incorrect example |
|------|-------------|-------------|
| Start with an ASCII letter | `stageId` | `_stageId`, `1stStage` |
| Use only letters, digits, and underscores | `stage_id`, `stageId2` | `stage-id`, `stage id` |
| Case sensitive | `assetName` when the definition says `assetName` | `assetname`, `AssetName` |
| Use the get_event_spec result as is for an event template's properties | `amountCurr` | an arbitrarily changed `currentAmount` |

The following reserved words cannot be used, regardless of case.

- attributes
- eventAttributes
- hiveAttributes

A name starting with `_` is reserved for properties the analytics pipeline processes, such as `_dataSource`, `_geoIpCountry`,
`_market`, and `_os`, so do not use it as a game custom property name.

### Values

The allowed values are numeric and string scalars.

| data_type | Send form | Example |
|-----------|-----------|------|
| INT | An unquoted number | `120` |
| STRING | A string | `"dia"` |
| TIMESTAMP | A string in `yyyy-MM-dd HH:mm:ss` format | `"2026-09-01 14:03:21"` |

An example of a TIMESTAMP event property is `2026-09-01 14:03:21`. Here `MM` is the month and `mm` is the minute, and
`HH` is a 24-hour clock. The required property eventTime does not follow this rule — it uses the RFC 3339 + time zone
format from section 3.

Objects, arrays, and JSON-shaped strings can be quarantined. Do not work around this with string serialization. Sending the same
property name twice can result in one being picked arbitrarily, so remove duplicate keys before assembling the payload.

## 5. Value Rules for Directly Sent Event Properties

This section's value rules apply to properties that `get_event_spec` defined as GAME, to common enrichment targets, and to an
AUTO property the user explicitly chose to send. `GAME` means the game is responsible for sending the property; `AUTO` means
the game does not need to send it by default, not that an explicit additional send is prohibited. When the user chooses to send
an AUTO property, explain that SDK v4 can overwrite the SDK-collected value under the same eventAttributes key, while Axyl can
retain same-named values separately in hiveAttributes and eventAttributes. This exception does not apply to the top-level appId
and userId columns; do not duplicate those as custom properties.

In Axyl, header values such as `os` and `lang` are auto-collected into hiveAttributes under the same names as the dimensions
below, as the header sent them (not converted to the Hive code value). When the event definition or the common enrichment
requires such a property, ask the user whether to use the hiveAttributes value or have the game send it into eventAttributes.
Only when they choose to send it, map it to the Hive code value per the rules below.

Do not send an engine API's display string as is.

| Property | Rule | Example |
|------|------|------|
| country | ISO 3166-1 alpha-2, uppercase | `"KR"` |
| lang | ISO 639-1, two lowercase letters | `"ko"` |
| os | Map the platform runtime value to the Hive OS code value | Android `"A"`, iOS `"I"` |
| market | Map the build's store target to the Hive market code value | Google Play `"GO"`, App Store `"AP"` |
| serverId | The runtime value of the server the current user is connected to | `"global-1"` |
| isPaid | The Y/N the definition requires | `"Y"`, `"N"` |

The examples above show only the shape of the value. Confirm the actual code value in the order below, and do not write the
mapping code before it is confirmed.

### Order for confirming a code value

For properties that use a Hive code value system, such as `os` and `market`, the full code table is not in this document.
Confirm it in this order.

1. Discover customer SDK event names. Call `query_adhoc` for the last 14 days with `event_name` omitted and
   `dimension_names=["_dataSource"]`. In the `hiveAttributes._dataSource` values, use only the exact direct-send value for the
   target SDK: `custom_sdk` for SDK v4 or `axyl_custom_sdk` for Hive Axyl. The matching value's `events` contains up to 10
   candidate event names. This is discovery only; do not infer a code system from the all-events aggregation.
2. Pick one or more of those customer SDK event names and query each one with the relevant dimensions (`os`, `market`, `_os`,
   `_market`, and so on). The event being integrated may not have been sent yet, so use an existing event discovered in step 1.
   Where each value lives depends on the SDK:

   | | SDK v4 | Hive Axyl |
   |---|---|---|
   | SDK auto-collected (`os`, `market`, and so on) | eventAttributes | hiveAttributes (`os`, `lang`, and so on; no `market`) |
   | Game custom properties | eventAttributes | eventAttributes |
   | Pipeline-processed, from appId (`_market`, `_os`) | hiveAttributes | hiveAttributes |

   This table covers logs the customer sends through the SDK. Hive platform logs (such as `_dataSource = hive_server`) can
   differ.

   `_market` / `_os` are always generated in both SDKs, but they are derived from appId, not from what the build sends — use
   them only as a reference.
   - **v4:** the SDK fills its default properties (`os`, `market`, `language`, and the others in section 2 of the SDK v4 flow)
     into eventAttributes, so the same property can appear twice — for example `hiveAttributes._market` from the pipeline and
     `eventAttributes.market` from the SDK. The game normally does not send these defaults (sending the same name overwrites
     the SDK value). When the game must send one anyway, follow the code system of the values already in eventAttributes.
   - **Axyl:** `os` can appear as `hiveAttributes.os` (the X-Platform header value as it arrived, such as `android`, not a Hive
     code), `hiveAttributes._os` (from the pipeline), and `eventAttributes.os` (only if the game sends it). The SDK does not
     collect `market` at all. Ask the user first: for `os`, whether to use `hiveAttributes.os` / `_os` or have
     the game send `os`; for `market`, whether `_market` is enough or the game should send `market`. If they choose to send
     it, follow the code system of the `eventAttributes` values the game already sends in the selected customer SDK events.
   Do not copy a value as a constant — derive it from the runtime (market from the build's store target, os from the platform)
   and map it to the code.
3. For both SDKs, compare the observed values with the target event's `get_event_spec.attributes[].desc_ko` convention and
   enumerated values. If they agree, the code system is confirmed. If only one source provides a convention, use it and state
   the evidence. If the historical values and the event specification conflict, treat it as contract drift and ask the user
   which contract should be corrected; do not silently prefer either one.
4. If the customer SDK events and the event specification do not confirm the mapping, or it is unclear which code a build or
   platform should map to, do not guess. Ask the user for the property's code value, and do not
   build the mapping until you have an answer.

For a new integration with no matching `_dataSource` history, move on to the event specification and then user confirmation.
Do not interpret an empty discovery result as `no code value`.

When sending os and market directly, take os from the platform runtime (`Application.platform`, and so on) and market from the build
flavor or store target settings. Sending the engine's display string (`"Android"`, `"IPhonePlayer"`, and so on) as is produces a
different code value and drops out of the aggregation, so map it to the Hive code value confirmed in the order above. If the
repository has no market distinction setting, do not decide arbitrarily — confirm with the user.

For serverId, find the server selection result, the login response, or the session state in the game code and use that. Do not invent candidate values.

Find the actual runtime source in the repository for every value. If the source value differs from the definition's convention,
build a mapping. If you cannot confirm the convention or the source, do not invent an arbitrary constant or conversion — raise it in the code review.

## 6. Send Diagnostics After an Actual Build

Even code that received only static checks or a limited compile must allow the Analytics send status and failure causes to be
checked after the actual game client is built and run.
To that end, always add a runtime diagnostic log at the central send point, using the repository's existing logging tools and error handling.

- Apply the same diagnostic approach to every event, in the repository's existing central wrapper or in a newly created central adapter.
  Do not force the name `HiveEventTransport.Send` or duplicate the implementation in per-event wrappers.
- For a send attempt, record only `eventName`, `guid`, and the processing stage.
- If the SDK provides a return value, exception, or callback, record the send API call result and the SDK error code and message.
- If the SDK API provides no result, do not record "send succeeded" — record no more than "SDK call completed".
- A successful SDK call is not the same as successful ingestion into the real store. For `query_adhoc`, use the AppID, eventName,
  and a narrow time range, and confirm actual ingestion by matching the returned rows' `eventAttributes.guid` against the guid in
  the client log. Do not put the guid directly in `filters`.
- Make the send-attempt and call-completed logs visible in development and QA builds, and follow the repository's log levels and
  build flags so repeated success logs do not flood the production logs.
- Follow the repository's production error collection policy for failure logs, but do not record the full payload, access tokens, or
  any event property value that could be personal information.
- Ensure that a failure of the diagnostic logging itself does not change game progression or the existing exception handling.
- Do not retry arbitrarily when a send failure is detected — tell the user.

Example log forms:

    [HiveAnalytics] send_attempt eventName=asset_get guid=<guid>
    [HiveAnalytics] sdk_call_completed eventName=asset_get guid=<guid>
    [HiveAnalytics] send_failed stage=sdk_callback eventName=asset_get guid=<guid> code=<code> message=<message>

The logs above are for checking the runtime send status. A build error at the compile stage occurs before the code runs, so it
cannot be checked through these logs — check the actual build system's error output.

## 7. Checking for Quarantine

When there is no normal ingestion, check for quarantine before concluding it is a delay.

Representative quarantine reasons:

- A directly sent required property is missing or empty
- Both appId and appIdGroup are absent
- A reserved word was used
- An object, array, or JSON-string property value
- An eventTime format or allowed-period violation
- Invalid JSON

Confirm the error type and the missing fields in the internal diagnostics, but do not record physical store names, error stacks, or
raw payloads in the customer report. Report only the field names needed and the masked error cause.
